# خطة تشغيل g000st بالكامل

آخر تحديث: 17 سبتمبر 2026

## الهدف

تحويل الواجهات الحالية من مطابقة بصرية جزئية إلى منتج فعلي يعمل عبر باك واحد، مع الحفاظ على
التصميم والسيناريو الموجودين في ملفات العميل القديمة، وتطبيق السلوك نفسه على Expo وNext.js.

نعمل بشرائح رأسية: لكل ميزة نثبت العقد، ثم الباك، ثم تطبيق الهاتف، ثم الويب، ثم الاختبارات. لا
ننشئ منطقًا وهميًا في الواجهة ولا نكرر قواعد العمل بين المنصتين.

## نتيجة التدقيق الحالية

### تطبيق الهاتف

- التسجيل واستعادة الحساب والجلسة تعمل مع API staging الحقيقي.
- `Chat` واجهة ثابتة فقط:
  - زر الإرفاق وزر الإرسال يحملان `disabled` صراحةً.
  - زر `g000st Social` لا يملك `onPress`.
  - لا توجد state للرسالة أو conversation أو messages.
  - لا توجد دوال Chat في طبقة API.
- حقل الرسالة لا يحمل `editable={false}`، ولذلك يجب أن يقبل الكتابة نظريًا. عدم قبوله في Android
  خلل مستقل سنعيد إنتاجه على جهاز متصل، والأرجح أنه متعلق بتخطيط الـscroll/keyboard الحالي لا
  بالمصادقة.
- `Contacts` واجهة ثابتة بلا handlers أو API.
- `ID & Profile` يعمل منه نسخ Public ID وتسجيل الخروج فقط.
- `Mobile` يعمل منه إدخال الأرقام وحذفها محليًا؛ الاتصال وSMS معطلان عمدًا.

### الويب والأدمن

- التسجيل والدخول والجلسة تعمل مع API الحقيقي.
- Chat يستخدم رسائل محلية وردًا آليًا مؤقتًا، ولا يستدعي `chatAPI`.
- Contacts وSocial وUsers Admin تعتمد بيانات mock في أجزاء أساسية.
- كثير من أزرار الاتصال والفيديو والدفع والدعم تعرض toast فقط.
- توجد ملفات API قديمة لمسارات مثل `/api/chat` و`/api/social`، لكنها لا تطابق base path الحالي
  ولا توجد لها مسارات مقابلة في الباك.

### الباك الحالي

- `apps/api` هو المصدر المعتمد ولا يعاد بناؤه من الصفر.
- المسارات الحقيقية المنشورة حاليًا هي health والمصادقة فقط.
- فحص `GET /api/v1/chat/conversations` على staging يرجع `404 NOT_FOUND`.
- Firestore مستخدمة للحسابات والجلسات، وسنستمر بها في هذه المرحلة.

### المرجع القديم

المرجع الأساسي للهاتف موجود خارج الريبو النظيف في:

`/Volumes/wold/projects/g000st-private-backup-20260917/legacy-root/appfg000st.html`

يحتوي المرجع على Chat وContacts وProfile وSocial وMobile ومرفقات وصوت وburn وغيرها، لكن جزءًا
كبيرًا منه يعتمد `localStorage` وبيانات تجريبية واتصالًا مباشرًا بـFirebase. كما أن SMS/Calls
كانت تحاول استعمال مزود الاتصالات من العميل. نحافظ على التجربة والتصميم، لكن ننقل الأسرار
وقواعد الصلاحيات إلى الباك ولا ننسخ هذا الأسلوب غير الآمن.

## القرارات المعمارية الثابتة

- المحادثات فردية فقط بين مستخدمين اثنين؛ لا غرف عامة ولا مجموعات.
- `/api/v1` هو العقد الوحيد للهاتف والويب والأدمن.
- Public ID للمشاركة والبحث، وRecovery ID سري للاستعادة فقط.
- الخادم هو الذي يستخرج هوية المرسل من access token؛ لا يقبل `senderId` من العميل.
- REST هو مصدر الحقيقة للقراءة والكتابة، وSocket.IO يستخدم للأحداث الفورية والتحديث.
- Firestore تخزن metadata والرسائل في المرحلة الحالية.
- الميديا ترفع إلى تخزين S3-compatible بروابط موقعة؛ لا توضع base64 في Firestore.
- أسرار Stripe ومزود الهاتف وFirebase تبقى في الخادم فقط.
- أنواع الطلبات والاستجابات وZod schemas توضع في package مشترك مثل `packages/contracts`.
- الويب وExpo يستخدمان نفس أسماء الحالات وقواعد التحقق ورسائل الأخطاء قدر الإمكان.
- لا نعرض ادعاء End-to-End Encryption قبل تطبيقه وتدقيقه فعليًا.

## المرحلة 0: تثبيت خط الأساس وحل التفاعل

1. مراجعة التعديلات المحلية الحالية في SafeArea وKeyboard وعدم الكتابة فوقها عشوائيًا.
2. تشغيل Android متصل بـADB وإعادة إنتاج مشكلة TextInput مع سجل واضح.
3. تحويل تخطيط Chat إلى:
   - header ثابت.
   - قائمة رسائل فقط هي القابلة للتمرير.
   - composer ثابت داخل حل keyboard معتمد.
4. جعل الحقل controlled عبر `value` و`onChangeText` وref واختبار focus والكتابة والأسطر المتعددة.
5. إبقاء Send معطلًا حتى توجد محادثة ونص صالح وAPI حقيقي؛ لا نضيف إرسالًا وهميًا.
6. إضافة حالات واضحة: loading، empty، offline، error، sending، retry.
7. تصوير baseline على Android وiOS والويب للمقارنة البصرية.

معيار النجاح: يمكن الكتابة وإظهار/إخفاء الكيبورد دون تغطية composer، وتبقى التابات قابلة
للاستخدام، ولا توجد رسالة وهمية أو زر صامت.

## المرحلة 1: Chat النصي الخاص — أول شريحة كاملة

### 1.1 عقد API والبيانات

نثبت عقدًا versioned للوظائف التالية:

- البحث عن مستخدم بواسطة Public ID.
- إنشاء أو جلب محادثة فردية بين مستخدمين.
- جلب قائمة المحادثات بآخر رسالة وعدد غير المقروء.
- جلب الرسائل باستخدام cursor pagination.
- إرسال رسالة نصية مع `clientMessageId` لمنع التكرار عند retry.
- تعليم الرسائل كمقروءة.
- إخفاء محادثة/رسالة من جهاز المستخدم فقط عندما نعتمد سياسة الحذف.
- حظر مستخدم والإبلاغ عن رسالة.

نموذج البيانات الأولي:

- `users`: الحالة والملف العام.
- `conversations`: مشاركان فقط و`pairKey` فريد مرتب.
- `conversation_members`: حالة كل مشارك، unread، وآخر قراءة/إخفاء.
- `messages`: المرسل، النوع، المحتوى، الوقت، وحالة الانتهاء إن اعتمدت.
- `message_receipts`: delivered/read عند الحاجة.
- `blocks` و`reports`: حماية ومراجعة إدارية.

### 1.2 باك Chat

- middleware مصادقة مشترك بدل استخراج bearer داخل كل router.
- تحقق عضوية المستخدم في كل conversation.
- Zod validation وحدود طول ورسائل rate limiting.
- Firestore transactions لإنشاء المحادثة وتحديث آخر رسالة والعدادات.
- cursor pagination وفهارس Firestore موثقة.
- Socket.IO مصادق عليه لإرسال:
  - `message.created`
  - `message.updated`
  - `message.read`
  - `conversation.updated`
  - presence عند اعتمادها.
- اختبارات خدمة ومتجر ومسارات تمنع القراءة أو الإرسال من مستخدم ثالث.

### 1.3 Expo Chat

- شاشة قائمة محادثات وحالة فارغة تقود إلى Contacts/Public ID.
- شاشة محادثة خاصة أو حالة محادثة فعالة داخل التاب حسب التصميم المعتمد.
- `FlatList` للرسائل مع pagination والحفاظ على موضع التمرير.
- composer حقيقي، optimistic message، retry، وفشل واضح.
- تحديث فوري عبر socket مع reconciliation ضد REST.
- SecureStore للجلسة فقط، وتخزين محلي مناسب للكاش/queue لا للأسرار.
- offline queue محدودة مع idempotency.
- navigation إلى Social عبر زر فعلي.

### 1.4 Web Chat

- حذف الرسائل التجريبية والرد الآلي.
- استخدام العقد وAPI وsocket نفسيهما.
- نفس حالات loading/empty/error/retry/read.
- responsive layout مطابق للهاتف في العرض الضيق.

### 1.5 اختبارات القبول

باستخدام حسابين حقيقيين على staging:

1. المستخدم A يجد B بواسطة Public ID.
2. يبدأ محادثة خاصة ويرسل رسالة.
3. تظهر فورًا عند B على منصة أخرى.
4. لا يستطيع C قراءة conversation أو إرسال رسالة إليها.
5. refresh يعيد نفس الرسائل دون تكرار.
6. انقطاع الشبكة ثم عودتها لا يكرر الرسالة.
7. انتهاء access token يجدد الجلسة دون ضياع draft.

## المرحلة 2: وظائف Chat المتقدمة

تنفذ بعد استقرار النص، بهذا الترتيب:

1. reply، reactions، edit، report، block.
2. read/delivered indicators وpresence.
3. الصور والملفات عبر media service وروابط موقعة.
4. الرسائل الصوتية مع صلاحيات الميكروفون ورفع streaming/file.
5. push notifications عبر Expo Notifications وFCM/APNs.
6. burn ومدة الاحتفاظ بعد اعتماد قواعدهما بدقة.
7. مكالمات الصوت والفيديو عبر WebRTC + signaling + TURN، وليس toast وهميًا.

كل وظيفة تنفذ في الباك وExpo والويب معًا قبل الانتقال لما بعدها.

## المرحلة 3: Contacts

- إضافة مستخدم بواسطة Public ID.
- QR حقيقي للـPublic ID ومسح QR في الهاتف.
- البحث والفلترة والمفضلة وonline.
- فتح Chat أو call من contact.
- block/remove محليًا أو على الحساب حسب القرار.
- فصل Contacts الخاصة بـg000st عن جهات هاتف Mobile العادية.
- صلاحية جهات اتصال الجهاز اختيارية وتطلب عند الاستخدام فقط.

## المرحلة 4: ID & Profile

- عرض ونسخ ومشاركة Public ID وQR.
- ملف اختياري: الاسم والصورة والعمر/الدولة/الهواية وفق حقول المنتج النهائية.
- رفع الصورة إلى media service.
- إدارة الجلسة والأجهزة وتسجيل الخروج.
- Recovery ID لا يظهر في الملف العام ولا يعود من `/auth/me`.
- الدعم والسياسات والبلاغات كمسارات حقيقية.

## المرحلة 5: Social

- feed حقيقي، نشر، تعديل، حذف، like، comments، share، report.
- profile اجتماعي واختيارات الخصوصية.
- Social Chat يعيد استخدام Chat الخاص نفسه، ولا ينشئ نظام رسائل ثانيًا.
- notifications حقيقية للمنشورات والتعليقات.
- إزالة جميع mock posts والاستجابات المحلية.

## المرحلة 6: g000st Mobile

هذه المرحلة تحتاج مزود اتصالات وقرارات تجارية قبل التنفيذ:

- فصل phone contacts عن g000st contacts.
- شراء/تخصيص رقم عبر الباك فقط.
- إرسال SMS وبدء call من الباك مع webhooks للتحقق من الحالة.
- رصيد واستهلاك يحسبان في الخادم لا في AsyncStorage/localStorage.
- Stripe للويب، ومراجعة متطلبات Apple/Google In-App Purchase للهاتف قبل بيع الخدمات الرقمية.
- سجل المكالمات وSMS والمفضلة مع صلاحيات وخصوصية واضحة.
- لا يوضع Telnyx/Twilio API key في Expo أو Next.js.

## المرحلة 7: الأدمن

- تعريف admin role ومصادقة وصلاحيات مستقلة ومدققة.
- مستخدمون حقيقيون: بحث، تعليق، إعادة تفعيل، وتقارير.
- إدارة البلاغات والمحتوى والدعم.
- مراقبة المدفوعات والاستهلاك دون عرض مفاتيح أو Recovery IDs.
- audit log لكل فعل إداري حساس.
- حذف mock users والإحصاءات الوهمية.

## المرحلة 8: التشغيل والجودة

- اختبارات unit وintegration لعقود وخدمات الباك.
- Firestore emulator في CI للاختبارات المعزولة.
- اختبارات مكونات/hooks للهاتف والويب.
- E2E لحسابين على staging لأهم السيناريوهات.
- فحص Android وiOS وأحجام الشاشات والكيبورد والصلاحيات.
- logs وerror monitoring دون محتوى الرسائل أو التوكنات.
- rate limits، quotas، نسخ احتياطي، واختبار استعادة.
- GitHub Actions منفصلة: checks ثم deploy يدوي إلى staging.
- لا يتحول `g000st.com` قبل checklist إطلاق وموافقة صريحة.

## ترتيب التنفيذ الفعلي

نعمل بالترتيب التالي ولا نفتح عدة أجزاء ناقصة بالتوازي:

1. إصلاح TextInput/keyboard وبنية Chat UI.
2. عقد وBackend Chat النصي الخاص.
3. Expo Chat النصي end-to-end.
4. Web Chat النصي بالعقد نفسه.
5. Chat المتقدم والميديا والإشعارات.
6. Contacts على الباك ثم Expo ثم الويب.
7. ID/Profile على الباك ثم Expo ثم الويب.
8. Social على الباك ثم Expo ثم الويب.
9. Mobile telephony/payments بعد توفير المزود والقرارات.
10. Admin الحقيقي.
11. QA شامل وتجهيز الإنتاج.

## قرارات يجب حسمها قبل ميزاتها

لا تمنع هذه الأسئلة بدء إصلاح الحقل وبناء Chat النصي، لكنها تمنع الادعاء بأن المنتج مكتمل:

1. هل المطلوب End-to-End Encryption فعلي، أم تشفير النقل والتخزين في المرحلة الأولى؟
2. هل قاعدة `Kept 2 hours` وحرق 5 ثوانٍ مطلوبة فعليًا؟ ومتى يبدأ العداد؟
3. هل الحذف من الجهاز فقط يعني إخفاء الرسالة عن جهاز واحد أم عن كل أجهزة الحساب؟
4. ما مزود الاتصالات النهائي: Telnyx أم Twilio أم غيرهما؟
5. هل Stripe هو مزود الدفع النهائي، وما المنتجات والأسعار الحقيقية؟
6. هل Social anonymous بالكامل أم يعرض profile اختياريًا؟

## تعريف الإنجاز

لا نعتبر زرًا أو صفحة منجزة لأنها تتحرك أو تعرض toast. تكون الميزة منجزة عندما:

- تملك عقد API موثقًا ومختبرًا.
- تحفظ وتقرأ بيانات حقيقية بصلاحيات صحيحة.
- تعمل على Expo والويب بالسيناريو نفسه.
- تعرض loading/empty/error/offline بصورة مفهومة.
- تنجح اختبارات حسابين وفشل الشبكة وانتهاء الجلسة.
- لا تحتوي أسرارًا في العميل ولا mock data في مسار الإنتاج.
