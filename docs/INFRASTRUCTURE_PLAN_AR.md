# خطة البنية التحتية لـ g000st

آخر تحديث: 16 سبتمبر 2026

## حالة التنفيذ

- نُشر إصدار الويب `9221123` كنسخة staging مستقلة على `127.0.0.1:3001`.
- يوجّه Nginx اسم `staging.g000st.com` إلى الويب، ومسار `/api/v1` إلى API staging على `127.0.0.1:3100`.
- أضيف نطاق staging إلى CORS، ونجح اختبار المصادقة الكامل بعد إعادة تشغيل API staging.
- أصبح `staging.g000st.com` متاحًا عبر HTTPS بشهادة Let's Encrypt وتجديد تلقائي.
- نجح اختبار المصادقة الكامل عبر النطاق العام المشفر، ثم حُذفت بيانات حساب الاختبار.
- الويب الحالي على المنفذ 3000 ونطاق `g000st.com` لم يتغيرا.

## القرار

نعتمد توزيعًا من خادمين مع فصل مسؤوليات واضح:

- `g000st-web` هو الخادم الأساسي: Nginx، تطبيق Next.js، وواجهة API الإصدارية.
- `g000st-app` يتحول إلى خادم ميديا بعد أرشفة التطبيق القديم والتحقق من عدم وجود حركة لازمة عليه.
- تبقى Firestore قاعدة البيانات في المرحلة الأولى؛ نقل البيانات إلى PostgreSQL قرار مستقل لاحق، وليس جزءًا من تحويل الويب والموبايل.
- لا تُحفظ الميديا كملفات عشوائية داخل تطبيق الويب أو الـAPI. تُخزن عبر واجهة S3-compatible مع روابط رفع وقراءة موقعة.

## الحالة الحالية المؤكدة

### الخادم الأساسي `g000st-web`

- 2 vCPU، وذاكرة 3.7GB، وقرص 38GB مع نحو 32GB متاحة وقت الفحص.
- يشغّل Nginx على 80/443.
- يشغّل نسخة الويب الحالية على المنفذ 3000 بواسطة PM2.
- يشغّل `g000st-api-staging` على `127.0.0.1:3100` بواسطة PM2.
- الباك القديم يستخدم Firebase Admin وFirestore، إضافة إلى Stripe وGroq.
- يوجد ملف SQLite حجمه نحو 20KB، لكن مسارات الباك الأساسية المقروءة تعتمد Firestore.
- لا توجد خدمة PostgreSQL أو MySQL أو MongoDB أو Redis محلية.
- توجد نسخة احتياطية يدوية قبل تأسيس مسارات المصادقة، ولا توجد بعد سياسة نسخ احتياطي دورية لبيانات المنتج.

### خادم التطبيق القديم `g000st-app`

- 2 vCPU، وذاكرة 3.7GB، وقرص 38GB مع نحو 29GB متاحة وقت الفحص.
- يشغّل التطبيق القديم بواسطة PM2، مع Nginx وCloudflare Tunnel.
- لا توجد قاعدة بيانات منتج محلية مستخدمة؛ ملف SQLite الموجود فارغ.
- لا توجد مكتبة ميديا فعلية أو مساحة تخزين مستقلة.
- المنافذ 3000 و8080 متاحة حاليًا للعامة، ويجب إغلاقها بعد نقل التطبيق القديم.
- بعض ملفات البيئة القديمة صلاحيتها `644`، ويجب تدوير أسرارها وتصحيح الصلاحيات قبل إعادة استخدام الخادم.

## متطلبات خادم الميديا

لا نبدأ تخزين ملفات الإنتاج على قرص النظام الحالي. قبل تشغيل خدمة الميديا نحتاج:

1. إضافة volume منفصل بحجم مناسب للنمو، أو اعتماد object storage خارجي متوافق مع S3.
2. تشغيل MinIO أو خدمة S3-compatible بحساب نظام مستقل، لا بحساب `root`.
3. نطاق مثل `media.g000st.com` مع TLS، ومنع الوصول المباشر إلى منفذ التخزين الإداري.
4. Buckets خاصة افتراضيًا؛ الرفع والقراءة بروابط قصيرة العمر وموقعة من الـAPI.
5. حدود لنوع الملف والحجم، والتحقق من MIME، وأسماء عشوائية غير قابلة للتخمين.
6. نسخة احتياطية خارج الخادم واختبار استعادة دوري. الخادم الثاني وحده ليس نسخة احتياطية.

## قواعد الأمان قبل الإنتاج

- تعمل Next.js والـAPI وخدمة الميديا على loopback أو شبكة خاصة فقط؛ Nginx هو المدخل العام.
- إغلاق المنافذ العامة 3000 و3001 و8080 بعد التحقق من التحويل.
- تشغيل الخدمات بحسابات نظام محدودة بدل `root`.
- حفظ ملفات البيئة وFirebase service account بصلاحية `600` خارج مجلدات الإصدارات.
- تدوير مفاتيح الملفات القديمة ذات الصلاحيات الواسعة بدل الاكتفاء بتغيير الصلاحية.
- تقييد CORS بالنطاقات الفعلية، وتطبيق rate limiting، وسجلات تدقيق دون أسرار أو Recovery IDs.
- أخذ snapshot قبل أي نقل، والاحتفاظ بإصدار سابق قابل للرجوع.

## مراحل التنفيذ

### المرحلة 1: تثبيت الباك الحالي

- اعتبار `apps/api` مصدر الباك الوحيد الجديد.
- إكمال المصادقة على staging: Public ID وRecovery ID والجلسات الدوارة.
- ربط الويب وExpo بنفس `/api/v1` وإجراء اختبارات تكامل حقيقية.
- إبقاء Firestore لتجنب دمج تحويل الواجهات مع ترحيل قاعدة بيانات في عملية واحدة.

### المرحلة 2: نشر الويب والـAPI

- بناء release غير قابل للتعديل من commit محدد.
- تشغيل الويب والـAPI بحسابي خدمة منفصلين خلف Nginx.
- اختبار health checks، التسجيل، الاستعادة، المحادثة الخاصة، وStripe قبل تحويل الحركة.
- إغلاق المنافذ الداخلية من الجدار الناري بعد نجاح Nginx.

### المرحلة 3: خدمة الميديا

- أخذ snapshot من `g000st-app` وأرشفة التطبيق القديم.
- إضافة volume أو object storage، ثم إعداد التخزين المتوافق مع S3.
- إضافة endpoints للروابط الموقعة وسياسة حذف واضحة.
- اختبار رفع وتنزيل وحذف واستعادة الملفات قبل استخدامه من الويب أو Expo.

### المرحلة 4: قرار قاعدة البيانات

بعد الوصول إلى تطابق وظيفي مستقر، نقيس احتياج البحث والعلاقات والتقارير. عندها فقط نقرر بين الاستمرار على Firestore أو ترحيل منظم إلى PostgreSQL. إذا اختير PostgreSQL، يجب أن يملك نسخًا احتياطية مشفرة واختبار استعادة، وألا يكون مكشوفًا للإنترنت.

## أشياء لم تتغير أثناء التدقيق

- لم تُوقف أو تُعد تشغيل أي خدمة.
- لم تُعدّل إعدادات Nginx أو PM2 أو UFW.
- لم تُقرأ قيم ملفات البيئة أو محتويات بيانات المستخدمين.
- لم يُنقل أي نطاق أو ملف إنتاج.
