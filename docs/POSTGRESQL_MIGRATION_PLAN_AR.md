# خطة نقل بيانات g000st إلى PostgreSQL

**الحالة:** خطة تنفيذ، لم يبدأ الترحيل. **أُنشئت:** 25 سبتمبر 2026. **آخر مراجعة للكود والخادم:** 30 سبتمبر 2026. راجع القسم 12 قبل اعتماد مكان القاعدة أو موعد القطع.

تغطي هذه المراجعة ما أُضيف بعد الخطة الأولى: صفحات الحسابات وحقول التواصل في الملف الشخصي، اقتراحات Social، حذف وإخفاء المحادثات والرسائل الصوتية وBurn، لوحة الأدمن وإعداداتها ورسائلها وتدقيق إجراءاتها، إحصاءات الأقسام، والفوترة في الواجهة. تُعتمد حالة الكود وقت بدء المرحلة 0 مرة أخرى؛ تاريخ هذه المراجعة ليس إثباتًا لنشر التغييرات على production.

## 1. القرار والهدف

- تصبح PostgreSQL مصدر الحقيقة الوحيد لبيانات المنتج: الحسابات وصفحاتها والجلسات، الملفات الشخصية، الأصدقاء، Social، Market، Chat، الحضور وسجل النشاط، الإشعارات المسجلة، المكالمات، SMS، الأرصدة وسجلها، إعدادات الأدمن، الرسائل والدعم، وسجل التدقيق.
- يبقى `apps/api` الواجهة الوحيدة للبيانات أمام الهاتف والويب. تبقى عقود `/api/v1` وسلوكها كما هي؛ أي تغيير ظاهر يمر بإصدار عقد صريح.
- يبقى Firebase Cloud Messaging لإشعارات مكالمات Android الضرورية. تبقى APNs لمكالمات iOS، وخدمة Expo Push لإشعارات التطبيق العادية. PostgreSQL تخزن تسجيلات الأجهزة وحالة الإرسال، لكنها لا ترسل Push بنفسها. يمكن تشغيل FCM من خادم API مستقل عن Firestore. [توثيق FCM](https://firebase.google.com/docs/cloud-messaging/fcm-architecture)
- تبقى ملفات الصور والصوت والفيديو في التخزين المتوافق مع S3/MinIO. PostgreSQL تخزن مفاتيح الكائنات والبيانات الوصفية فقط؛ تبقى Stripe وTelnyx وTURN خارج قاعدة البيانات بوصفها خدمات مستقلة.
- تحديد البلد والمدينة من IP يحتاج مصدر بيانات مستقلًا عن PostgreSQL، مثل قاعدة MaxMind City محلية ومحدَّثة أو ترويسات موقع من وكيل موثوق. تخزن PostgreSQL الموقع التقريبي الناتج ووقت رصده، ولا تعطي اسم المدينة من IP وحده. لا نفعّل `TRUST_GEO_HEADERS` قبل إعداد مصدر موثوق ومسح ترويسات الموقع التي يرسلها العميل.
- لا نعيد بيانات العميل القديمة من فرع الأرشيف إلى `main`. يشمل النقل بيانات `apps/api` الفعلية في بيئاتها المعتمدة فقط.

هذه الخطة تحل محل قرار التأجيل السابق في [خطة البنية](INFRASTRUCTURE_PLAN_AR.md)، بعد موافقة صاحب المشروع على الانتقال. لا تعني الموافقة بدء تحويل بيانات الإنتاج أو حذف Firestore؛ ذلك يحدث فقط عند بوابات القطع أدناه.

## 2. صورة الوضع الحالي

| المجال | المصدر الحالي في API | ملاحظات النقل |
| --- | --- | --- |
| Auth وصفحات الحسابات | `FirestoreAuthStore` | حسابات، دور admin، صفحات مملوكة لحساب بشري وتُستخدم بجلسة مالكها، بصمة Recovery ID، جلسات access/refresh وعائلاتها؛ لا يوجد Recovery ID صريح في الخادم. |
| Social وMarket | `FirestoreSocialStore`, `FirestoreMarketStore` | منشورات ووسائط وتعليقات وتفاعلات ومتابعة وتنبيهات وبلاغات؛ إخفاء/حذف إداري للمنشورات؛ اقتراحات Social مشتقة يوميًا من العلاقات والحسابات، ولا يوجد مخزن مستقل لها. الملف الشخصي يضم صورة وغلافًا وبلدًا اختياريًا وحقول تواصل جديدة، منها WhatsApp والهاتف الأرضي والبريد وروابط الشبكات؛ بلد الملف الشخصي ليس بلد الاتصال. |
| Chat وContacts وPresence | `FirestoreChatStore`, `FirestoreContactsStore`, `FirestorePresenceStore` | محادثات خاصة ومحادثات Market، تلخيص لكل عضو وإخفاء محادثة لكل عضو، رسائل نصية وصوتية ومرفقات، حذف رسالة للمرسل، Burn ومواعيد انتهاء، أسماء أصدقاء، آخر نشاط وموقع مرصود إن توفر. لا يوجد حاليًا سجل تاريخي لكل يوم نشاط. |
| Notifications وCalling | `FirestoreNotificationStore`, `FirestoreCallingStore` | أجهزة Expo Push، رموز VoIP، سجل المكالمات؛ FCM يعتمد اليوم على تهيئة Firebase Admin التي ينشئها Firestore. |
| Billing وTelephony | `FirestoreBillingStore`, `FirestoreTelephonyStore` | أرصدة وحدات، دفتر قيود idempotent، مكالمات/SMS Telnyx وwebhooks. |
| الأدمن والتواصل والإحصاءات | `AdminDeskService`, `AdminAnalyticsService` | خدمتان تصلان إلى Firestore مباشرة دون Store interface: `admin_config`, `admin_messages`, `support_inbox`, `admin_issued_accounts`, `admin_audit`، مع قراءة الحسابات والمنشورات والحضور والأرصدة. إنشاء حساب من الأدمن يعرض Recovery ID مرة واحدة؛ تُحفظ ملاحظة الإصدار فقط. لوحة المستخدمين والفوترة تعرضان بيانات فعلية. |

تجميع الخدمات الحالي موجود في [`apps/api/src/server.ts`](../apps/api/src/server.ts). أغلب المجالات تملك `*Store` interface بالفعل، لكن خدمات الأدمن لا تملكه ويجب فصل وصولها إلى قاعدة البيانات قبل القطع. لا نربط العملاء بقاعدة البيانات ولا نعيد بناء API من الصفر. تُحفظ عقود `v1` الحالية، ومنها [`ADMIN_DASHBOARD_V1_AR.md`](ADMIN_DASHBOARD_V1_AR.md) و[`CHAT_API_V1.md`](CHAT_API_V1.md).

## 3. البنية المستهدفة

```text
Mobile / Web  --> HTTPS --> apps/api --> PostgreSQL (محليًا أو عبر شبكة خاصة)
                               |-----> MinIO / S3 (الملفات)
                               |-----> Expo Push / FCM / APNs (الإشعارات)
                               |-----> Stripe / Telnyx / TURN (الخدمات الخارجية)
               Nginx/GeoIP -----------> بلد/مدينة تقريبية إلى API
```

1. **الاستضافة:** يمكن تشغيل PostgreSQL محليًا على `g000st-web` للتجربة بعد اجتياز قياسات القسم 12، لكن ذلك يجعل الويب وAPI وTURN والقاعدة على نقطة فشل واحدة. لا تكفي لقطة الموارد الحالية لاعتماد هذا الترتيب إنتاجيًا. عند تجاوز حدود الموارد أو الحاجة إلى توافر عالٍ تُنقل القاعدة إلى خادم خاص داخل شبكة خاصة. لا نختار حجم القاعدة أو موعد القطع قبل قياس البيانات والضغط والنسخ والاستعادة.
2. **الفصل:** قاعدتان منفصلتان لـstaging وproduction، بمستخدم تطبيق محدود الصلاحيات لكل بيئة ومستخدم migrations منفصل. لا تستخدم `AUTH_COLLECTION_PREFIX` لتقليد فصل البيئات في SQL. عند التثبيت المحلي يُقصر الاتصال على Unix socket أو `127.0.0.1` مع SCRAM وصلاحيات محدودة؛ وعند فصل الخادم تُستخدم شبكة خاصة وTLS ولا يُفتح منفذ عام. [توثيق مصادقة PostgreSQL](https://www.postgresql.org/docs/current/auth-password.html)
3. **الربط:** pool واحد مضبوط لكل عملية API، بحد اتصالات مشتق من عدد عمليات PM2 وحد `max_connections`. timeouts للاستعلامات والمعاملات وhealth check حقيقي لقاعدة البيانات. migrations محفوظة في `apps/api` وذات رقم إصدار؛ تُشغّل كخطوة نشر مستقلة قبل تحويل الكود، ولا تُشغّل تلقائيًا من كل نسخة API.
4. **Firebase المتبقي:** نفصل تهيئة Firebase Admin اللازمة لـFCM عن `createFirestore()`. عندما تختفي آخر Store من Firestore، لا نُبقي `getFirestore()` في بدء التشغيل. تُحصر بيانات اعتماد FCM في الخادم؛ يظل تسجيل أجهزة Expo/VoIP في PostgreSQL.
5. **الزمن والملفات:** تخزين الوقت في `timestamptz` UTC، والتحويل من/إلى `*AtMs` عند حد Store حتى يبقى عقد API كما هو. لا تخزين base64 أو ملفات ثنائية في SQL.
6. **الموقع:** يحدد الوكيل الموثوق أو API البلد والمدينة من IP الاتصال بمصدر GeoIP محلي ومحدَّث؛ PostgreSQL تستقبل النتيجة ولا تحتاج PostGIS لهذا الغرض. يحتفظ `presence` بآخر موقع مرصود، بينما يتطلب إحصاء نشاط المدن عبر الزمن صفوف نشاط يومي جديدة. لا نعتمد بلد الملف الشخصي ولا بيانات مكان أرسلها العميل.

## 4. نموذج البيانات الأولي

هذه خريطة تصميم وليست SQL نهائيًا. تُعتمد DDL والقيود بعد جرد الحقول الفعلية والعينات في المرحلة 0. نستخدم مفاتيح Public ID الحالية ومعرّفات المستندات القائمة؛ لا نولّد هوية جديدة أثناء الترحيل.

| مجموعة الجداول | الجداول المقترحة | قيود وفهارس مهمة |
| --- | --- | --- |
| الهوية والصفحات | `accounts`, `account_pages` أو علاقة `owner_id` في `accounts`, `recovery_credentials`, `session_families`, `access_sessions`, `refresh_sessions` | Public ID فريد للحساب والصفحة؛ الصفحة لا تملك Recovery ID أو جلسة مستقلة؛ دور admin وحالة active/suspended/deleted؛ lookup hash فريد وhash فقط للأسرار والرموز؛ فهارس انتهاء الصلاحية وfamily؛ حفظ replay detection. |
| الملف والعلاقات | `profiles`, `contacts`, `follows`, `presence` | حفظ حقول التواصل الجديدة والصورة والغلاف و`show_display_name` مع حدود الإظهار؛ `(owner_id, contact_id)` وفهرس المتابعة فريدان؛ الاسم البديل خاص بصاحب القائمة. `presence` يحفظ آخر نشاط وبلد/مدينة اتصال ووقت رصده، مستقلًا عن بلد الملف الشخصي. |
| نشاط وإحصاءات الأدمن | `user_activity_days`, `user_location_days`، مع استعلامات تجميع على جداول المنتج | صف مميز لكل مستخدم/يوم UTC للنشطين يوميًا وشهريًا؛ صف لكل مستخدم/يوم/موقع مرصود لتوزيع الدول والمدن مع منع تكرار heartbeats. تُحدد قاعدة عدّ من ظهر في بلدين في يوم واحد قبل DDL، وتُفهرس الفترة والبلد والمدينة. إحصاءات الأقسام تُحسب من الجداول الأصلية أو ملخصات مشتقة قابلة لإعادة البناء؛ لا نقل لعدادات cache باعتبارها مصدر حقيقة. |
| Social | `social_posts`, `social_post_media`, `social_comments`, `social_reactions`, `social_alerts`, `social_reports` | حفظ `visibility` و`shared_post_id`، والحقول الإدارية `hidden` و`deleted_at`؛ منشور مخفي لا يظهر حتى عبر طلب ID مباشر. قيود مالك وتفاعل فريد وفهارس cursor؛ الاقتراحات اليومية تُعاد حسابها من العلاقات والحسابات، دون ترحيل cache غير موجود. |
| Market | `market_posts`, `market_post_media`, `market_comments`, `market_reactions`, `market_reports` | السعر بقيمة عشرية محددة الدقة والعملة، مع `allow_calls` و`allow_video_calls`، والإخفاء والحذف الإداري؛ فهارس feed والمالك؛ media object key فقط. |
| Chat | `conversations`, `conversation_members`, `chat_messages`, `chat_attachments` | حفظ `kind` و`market_post_id`، `hidden_at` لكل عضو، الملخصات وread state، النص/الصوت/المرفقات، `locked`, `burn_after_read_seconds`, `burn_started_at`, `expires_at`، وحذف رسالة للمرسل. مفتاح زوج مرتب وفريد لكل نوع محادثة، `(conversation_id, sender_id, client_message_id)` فريد؛ فهارس cursor والانتهاء. |
| الإشعارات والمكالمات | `push_devices`, `voip_devices`, `calls`, `outbox_events` | `(public_id, device_id)` فريد؛ رموز الأجهزة خاصة؛ `outbox_events` يحفظ العمل الخارجي القابل لإعادة المحاولة بعد commit. |
| الفوترة والهاتف | `billing_balances`, `billing_ledger`, `telephony_calls`, `telephony_sms`, `webhook_events` | مفتاح idempotency فريد لكل أثر مالي، تحديث الرصيد والدفتر في معاملة واحدة؛ معرفات Stripe/Telnyx/webhook فريدة؛ ترتيب سجلات cursor مركب. |
| الإدارة والتواصل | `admin_config`, `admin_messages`, `support_inbox`, `admin_issued_accounts`, `admin_audit` | الحفاظ على مفاتيح pages/parts وتسمياتها، الرسائل العامة والخاصة والتحذيرات، حالة الرد وصندوق الدعم، ملاحظات الحسابات الصادرة دون Recovery ID، وسجل إجراءات الأدمن غير القابل للتعديل. الرد على رسالة دعم وإنشاء إشعارها وتدقيقها عملية ذرية. تحفظ مفاتيح actor/target حتى مع حذف الحساب أو تعتمد مراجع قابلة للإلغاء دون فقد التدقيق. |

**قواعد لا تُفقد أثناء النقل:** لا تخزين Recovery ID الصريح، حتى للحساب الذي يصدره الأدمن. الحساب المحذوف لا يستطيع الدخول أو الإرسال، وتبقى الآثار التي يتطلبها المنتج باسم `Deleted account`. تسجيل الدخول العادي قد يعطَّل من `admin_config` مع استمرار دخول الأدمن؛ ولا تُصبح مفاتيح إخفاء أجزاء الويب سياسة API أو الهاتف دون قرار منتج منفصل. رسائل Chat الخاصة العادية لا تُحذف بعد ساعتين؛ حد الساعتين يخص ظهورها في واجهة الهاتف. رسائل Market تنتهي بعد 30 يومًا، وBurn يبدأ عند الفتح وينتهي بعد 60 ثانية وفق `chat-policy.ts` الحالي. لا تُنسخ الرسائل المنتهية أو المحذوفة فعليًا، مع اختبار استثناءات البيانات القديمة. لا تُفقد مفاتيح الوسائط أو العلاقة بين الرسالة/المنشور/الملف؛ وتُراجع سياسة الاحتفاظ بنص SMS والبلاغات وwebhooks ورسائل الدعم وسجل التدقيق قبل تثبيت DDL.

## 5. قواعد التنفيذ في الكود

- ننشئ `Postgres*Store` مطابقًا لكل interface موجود، مع اختبارات عقد مشتركة تشغّل السلوك نفسه على بديل Firestore وPostgreSQL حيث أمكن. لا نضع SQL في `apps/mobile` أو `apps/web`.
- نعزل استعلامات وكتابات `AdminDeskService` و`AdminAnalyticsService` خلف واجهتي تخزين صريحتين قبل نقل الأدمن. تشمل العمليات إصدار حساب مع ملاحظته، الحظر وتعديل الاسم، إخفاء وحذف Social/Market، flags وlabels، الرسائل والتحذيرات والدعم والتدقيق، البحث والتصفح، وأرصدة الفوترة. لا يبقى مسار API أدمن يقرأ Firestore بعد القطع.
- ترتبط `AuthService` اليوم بإعداد `pages.login` من خدمة الأدمن؛ ينتقل هذا الفحص إلى مصدر PostgreSQL نفسه قبل القطع، مع اختبار أن إغلاق الدخول يمنع التسجيل والاستعادة العاديين ويبقي وصول الأدمن وإصدار حساب من الأدمن متاحين. عند إصدار حساب، تحفظ بيانات الحساب وملاحظة الإصدار وسجل التدقيق في معاملة واحدة، ويظل Recovery ID في الذاكرة والرد فقط دون أي تخزين أو سجل.
- نعزل المنطق المشترك، مثل بناء cursors والتحقق من العضوية، في الخدمات الحالية؛ تتولى Stores القراءة والمعاملات. تُستبدل وثائق Firestore الفرعية بصفوف وجداول علاقات، ولا ننقل شكل المستندات حرفيًا إلى عمود JSONB عام.
- لكل عملية تعدّل عدة جداول، معاملة قصيرة وواضحة. قفل الصف المناسب في الرصيد، read state، وتدوير refresh؛ فهارس uniqueness تمنع التكرار عند السباق. لا يُجرى نداء Stripe/Telnyx/FCM داخل معاملة SQL.
- نستخدم outbox للآثار التي لا يمكن ضمها ذريًا إلى SQL (Push، حذف ملف MinIO، وبعض webhooks) مع worker وإعادة محاولة ومفتاح idempotency. ذلك مهم خاصة بعد حذف رسائل Chat وانتهاء صلاحيتها.
- نحافظ على `clientMessageId` وcursors والقيود الأمنية الموجودة. يكون استعلام كل feed بترتيب ثابت، ويُقارن الناتج مع Firestore قبل أي قطع.
- يكون تسجيل النشاط اليومي idempotent بمفتاح `(user_id, day_utc)`، وتسجيل الموقع اليومي بمفتاح يمنع تكرار نبضات المستخدم في المكان نفسه. لا ننشئ صف حدث لكل heartbeat؛ تبقى `presence` للاتصال الآني ويُحفظ الحد الأدنى الكافي للإحصاء التاريخي. تُحسب DAU وMAU من مستخدمين مميزين وفق التعريف المنشور في عقد الأدمن، وتُستبعد صفحات الحسابات والمحذوفون حسب سياسة العد المعتمدة. تُحدد سياسة الاحتفاظ بالنشاط والموقع قبل بدء جمعهما.
- نستخدم مصدر GeoIP موثوقًا ومحدَّثًا عند طبقة الوكيل/API، ونحفظ البلد والمدينة ووقت الرصد وربما معرّف المصدر/إصداره، لا IP الخام في جداول التحليلات. قيم `X-Geo-*` التي يرسلها العميل تُمحى عند حد الثقة. إذا غاب المصدر تُعرض «غير متاح» ولا يُستعاض عنه ببلد الملف الشخصي. حقول المدينة تبقى تقريبية وقد تكون فارغة.
- تُنفَّذ إحصاءات الأقسام في SQL باستعلامات وفهارس مناسبة، ثم ملخصات دورية فقط إذا أثبتت القياسات الحاجة؛ لا ننقل مسح `collectionGroup` الحالي كما هو إلى استعلام شامل غير محدود. يبقى تعريف كل مؤشر (posts/listings/conversations/follows/calls/SMS/ledger/reports/support) في عقد `v1` أو يصدر عقد جديد إذا تغير المعنى.
- تبقى بيانات اعتماد PostgreSQL وFirebase وStripe/Telnyx في بيئة الخادم فقط، خارج المستودع. لا تُكتب Recovery IDs أو tokens أو نصوص الرسائل في logs أو أدوات المقارنة.

## 6. طريقة ترحيل البيانات

### 6.1 الجرد والتحضير

1. جرد كل collections وsubcollections والعدادات والحقول الفعلية لكل بيئة، مع عدد المستندات وحجمها ومعدل التغيير اليومي؛ ربطها بالجدول المستهدف وتوثيق الحالات غير المعتادة. يشمل الجرد الجديد `admin_*` و`support_inbox` ومحتوى صفحات الحسابات وحقول التواصل و`presence` الجغرافي وعلامات الإخفاء والحذف، ورسائل Chat الصوتية و`hiddenAtMs` وBurn. تُراجع commits التي تأتي بعد هذه المراجعة قبل تثبيت المخطط.
2. تصنيف البيانات: مصدر حقيقة، بيانات مشتقة يمكن إعادة حسابها، بيانات منتهية، وأسرار. تحدد عينة staging مجهولة الهوية أخطاء الأنواع والحقول المفقودة من دون نشر أسرار.
3. نسخة احتياطية لـFirestore قبل كل تجربة قطع. تصدير Firestore المُدار صالح للاحتفاظ والاستعادة إلى Firestore، لكنه **ليس ملف SQL جاهزًا** ولا لقطة متطابقة تمامًا عند بداية التصدير؛ لذلك نبني قارئ ترحيل محكومًا من Admin SDK أو مرحلة تحويل صريحة، مع watermark/نافذة كتابة مجمدة. [توثيق Firestore للتصدير](https://firebase.google.com/docs/firestore/manage-data/export-import)
4. قياس سعة PostgreSQL المتوقعة: حجم الصفوف والفهارس والـWAL والنمو والنسخ الاحتياطي، ثم اختيار حجم الخادم وموقعه وميزانية شهرية. لا نفترض أن PostgreSQL أو Firestore أوفر قبل قياس القراءة والكتابة والتشغيل.

### 6.2 النقل التجريبي والقابل للإعادة

1. migrations SQL بإصدارات ثابتة، ثم برنامج `apps/api/scripts` مكتوب TypeScript للقراءة على دفعات وكتابة idempotent إلى staging. يحتفظ بمعرّفات المصدر ويرصد تقدم كل مجموعة في جدول `migration_runs` أو ملف حالة آمن خارج Git.
2. ترتيب الأب/الابن: accounts وصفحاتها ثم credentials/sessions/profiles، ثم العلاقات والمنشورات والوسائط، ثم المحادثات والأعضاء والرسائل، ثم أجهزة Push والمكالمات، ثم الأرصدة والدفتر والهاتف، ثم إعدادات الأدمن ورسائله والدعم والتدقيق. ينقل `presence` الحالي بوصفه آخر نشاط/موقع فقط؛ لا تُنشأ أيام تاريخية أو مدن قديمة من التخمين. تؤجل FKs التي تعيق الاستيراد إلى ما بعد التحقق مع معالجة tombstones.
3. تحويل Firestore Timestamp وأرقام الميلي ثانية إلى UTC؛ حفظ المال/السعر بدقة مناسبة؛ التعامل مع مستندات ناقصة، ردود الفعل المكررة، المراجع اليتيمة، حالات الحذف، والمجموعات الفرعية. لا نعيد حساب أرصدة مالية من تخمين؛ نقارن الرصيد مع مجموع ledger ونحقق الفروق يدويًا.
   ننقل قيم `salt` و`verifier` وlookup hash وعائلات الجلسات والرموز المجزأة كما هي. يبقى `AUTH_RECOVERY_PEPPER` نفسه أثناء النقل؛ تغييره من دون إجراء تدوير مصمم سيمنع استعادة الحسابات. بعد القطع نتحقق من دخول حساب قديم وتدوير refresh token قديم ومنع إعادة استخدامه.
4. جرد عدد الصفوف لكل مجموعة ومفاتيح المستندات، ومقارنة مجموعات عينات عشوائية وآخر/أول صفحة لكل cursor، وإعادة حساب العدادات المشتقة ومقارنتها. تُقارن أيضًا أعداد الحسابات البشرية منفصلة عن الصفحات، آخر نشاط، أرصدة المستخدمين وسجلها، flags وlabels، الصندوق المفتوح، الرسائل العامة والخاصة، السجلات المخفية والمحذوفة، وتدقيق الأدمن. تقارير المقارنة تخزن IDs أو hashes فقط ولا تحمل أسرارًا.
5. تشغيل migration dry run كامل على نسخة staging ومعه اختبار استعادة نسخة PostgreSQL. ثم تشغيل تطبيق staging فعليًا فوق PostgreSQL مع اختبار مستخدمين على الهاتف والويب.

### 6.3 التحويل الفعلي

**مسار القطع بحسب قرار الاحتفاظ بالبيانات:** نبني ونختبر Stores مجالًا مجالًا في التطوير وstaging، ثم نحوّل مصدر الحقيقة للإنتاج كله دفعة واحدة. إن تقرر نقل جميع البيانات، يلزم التقاط كل كتابة بعد النسخ الأولي بآلية سجل تغييرات/مزامنة موثوقة ثم إعادة تشغيلها بترتيبها والتحقق من المصالحة قبل تحويل التوجيه؛ لا يحقق تصدير Firestore وحده ذلك. إن تقرر تصفير المحتوى التجريبي، يمكن إعداد PostgreSQL بالتوازي ونقل الهوية والجلسات وإعدادات الأدمن وما لا يجوز إسقاطه فقط، ثم تحويل طلبات جديدة إلى API الجديد بعد تصريف الطلبات القديمة. لا تُسقط مدفوعات أو أرصدة أو webhooks حقيقية بقرار تصفير تجريبي. كلا الخيارين يحتاج بوابة كتابة قصيرة ومقاسة أو بروتوكول تنسيق أقوى بين المصدرين؛ لا نَعِد بصفر أخطاء أو صفر فقد لمجرد تشغيل نسختين. تفاصيل التشغيل وحدود الوعد في القسم 12.

**ترتيب البناء والاختبار في staging:** Presence/سجل النشاط/Contacts، ثم Social/Market، ثم Notifications/Calling، ثم Chat، ثم Auth وصفحات الحسابات، ثم Billing/Telephony كوحدة واحدة، وأخيرًا Admin/Communication/Analytics بعد اكتمال مصادرها. قبل تجربة cutover كاملة نعيد نسخ Accounts وكل المراجع من لقطة واحدة، ونختبر إنشاء/حذف الحساب أثناء عمل بقية الخدمات. لا نطبّق FK عابرًا لمصدرين أثناء التجارب الجزئية. نختبر أن لوحة الأدمن لا تعود إلى Firestore إذا فشل استعلام PostgreSQL.

**الرجوع:** قبل فتح الكتابات على PostgreSQL، يمكن الرجوع إلى Firestore بعد التحقق من أن النسخة الأصلية لم تتغير. بعد فتح الكتابات، تبديل العلم وحده إلى Firestore غير آمن؛ يتطلب إيقاف الكتابة، نقل العمليات الجديدة عكسيًا والتحقق منها، وإلا نصلح PostgreSQL للأمام. يحتفظ الفريق بنسخة Firestore للقراءة فقط فترة مراقبة محددة بعد القطع، ثم تؤرشف وتحذف ضمن سياسة الاحتفاظ. لا يُحذف أي مصدر قبل نجاح النسخ الاحتياطي والاستعادة وموافقة تشغيلية صريحة.

## 8. الاختبارات ومؤشرات النجاح

- اختبارات API الحالية كلها، ثم اختبارات تكامل PostgreSQL حقيقية لعمليات auth refresh المتزامنة، إنشاء/استخدام صفحات الحسابات، الحذف، جلب feed والبحث عن المستخدمين بالـcursor، تكرار `clientMessageId`، read/unread، إخفاء محادثة لكل عضو، حذف رسالة وصوت/مرفقاتها، Burn بعد 60 ثانية، انتهاء Market Chat، race على follow/like، وتكرار Stripe/Telnyx webhooks.
- اختبارات عقد الأدمن: صلاحية admin على كل endpoint، حظر الحساب ودوره، إغلاق الدخول مع بقاء دخول الأدمن، flags وlabels، الإخفاء والحذف الإداري للمنشورات، إصدار حساب دون حفظ Recovery ID، الرسائل العامة والخاصة، رد الدعم وسجل التدقيق الذري. اختبارات النشاط: DAU/MAU مميزان عبر تكرار heartbeat، حدود UTC، بلد/مدينة من مصدر موثوق فقط، وعدم عرض موقع عند غياب المصدر.
- فحوص end-to-end على staging: حساب جديد واستعادة حساب قديم، دخول من جهازين والتبديل إلى صفحة حساب، Social/Market والوسائط وحقول التواصل، Friends وChat بنص وصوت وBurn وإخفاء محادثة، إشعار Expo عادي، مكالمة Android عبر FCM وiOS عبر APNs، شراء/رصيد وSMS تجريبي، ثم رحلة أدمن تشمل مستخدمين حقيقيين وفوترة ورسائل ودعم ومفاتيح الصفحات وإحصاءات. تبقى اختبارات الأجهزة الحقيقية لازمة للخدمات التي لا تكفي محاكاتها.
- جرد قبل/بعد لكل جدول من حيث العدد والمفاتيح، مقارنة عينات كاملة بعد حذف الحقول الحساسة، تحقق المراجع والعدادات وledger balance، عدد الأجهزة النشطة، الرسائل غير المنتهية، إعدادات الأدمن وصندوق الدعم وسجل التدقيق، وتطابق أول وآخر صفحات feed والمستخدمين. تُوثق فجوة الإحصاءات التاريخية السابقة لبدء جمع النشاط اليومي بدل ملئها بأرقام تخمينية.
- مراقبة p50/p95/p99 للاستعلامات وAPI، أخطاء SQL وpool، deadlocks، معدل نمو WAL/القرص، replication/backup lag، عمر آخر نسخة ناجحة، backlog للـoutbox وchat expiration. تحدد حدود إنذار رقمية من baseline المرحلة 0، لا من أرقام تخمينية.
- بوابة الإنتاج: صفر فروق غير مفسرة في الحسابات وصفحاتها والرصيد والدفتر وإعدادات الأدمن؛ صفر فقد لرسائل غير منتهية أو رسائل دعم غير مجابة في العينة الكاملة؛ جميع اختبارات العقد والـE2E ناجحة؛ لا اعتماد متبقٍ على Firestore في API الأدمن؛ نسخ احتياطي حديث واستعادة مُجرّبة؛ نافذة قطع موثقة؛ المسؤول التشغيلي حاضر.

## 9. التشغيل والأمن والنسخ الاحتياطي

- نسخة أساسية دورية + أرشفة WAL خارج خادم قاعدة البيانات ومشفرة، مع اختبار استعادة شهري على بيئة منعزلة. هدف أولي قابل للتعديل بعد المرحلة 0: **RPO ≤ 15 دقيقة، RTO ≤ ساعتين**. تُراقب فجوات أرشفة WAL، ولا يُعد `pg_dump` وحده بديلًا عن PITR. [توثيق PostgreSQL لـPITR](https://www.postgresql.org/docs/current/continuous-archiving.html)
- منفذ قاعدة البيانات غير عام؛ اتصال محلي فقط عند الاستضافة على `g000st-web`، أو TLS عبر شبكة خاصة عند فصلها. تُستخدم SCRAM وحسابات منفصلة للتطبيق والترحيل والنسخ والقراءة التشغيلية، وتدوير الأسرار وfirewall وتشفير النسخ الاحتياطية. لا يستخدم API حساب superuser. تُراجع استعلامات بطيئة وامتيازات الوصول بانتظام.
- تحديد retention للرسائل المنتهية، بيانات الأجهزة، SMS، التنبيهات وwebhooks والدعم والتدقيق وسجل النشاط والموقع بالتعاون مع متطلبات المنتج والقانون. تحديث قاعدة GeoIP ومراقبة عمرها مهمة تشغيلية مستقلة؛ عند فشلها لا ندّعي مدينة صحيحة. نسخ PostgreSQL وحدها لا تغطي ملفات MinIO أو إعدادات Firebase/FCM أو قاعدة GeoIP؛ لكل منها إجراء تحديث/استعادة مناسب.
- تحديث نشر `infra/deploy/deploy-staging.sh`: migrations قبل تفعيل إصدار API متوافق، مع قاعدة expand/contract للتغيير غير القابل للتراجع آليًا. rollback كود PM2 الحالي لا يعيد مخطط DB، ولذلك يمنع نشر migration تكسر الإصدار السابق مباشرة.

## 10. قرارات مطلوبة عند بدء المرحلة 0

1. استضافة PostgreSQL محليًا على `g000st-web` إذا نجح قياس القسم 12، أم خادم خاص/خدمة مُدارة؛ البلد/المنطقة والميزانية الشهرية ومخاطر نقطة الفشل الواحدة.
2. حجم البيانات الحالي، معدل النمو المتوقع، وهل المطلوب تصفير محتوى التجربة فقط أم الحسابات والجلسات أيضًا، والحد المقبول لتأخير طلب الكتابة عند القطع.
3. أهداف RPO/RTO النهائية، مدة الاحتفاظ بالنسخ، ومتطلبات الخصوصية لرسائل Chat وSMS.
4. ما إذا كانت هناك بيانات إنتاج حقيقية في Firestore أو Stripe/Telnyx يجب نقلها كاملة، وأي مجموعات تجريبية يمكن استبعادها؛ يتم ذلك بجرد فعلي، لا بافتراضات الوثائق القديمة.
5. مصدر البلد/المدينة المعتمد (قاعدة MaxMind محلية محدَّثة أو وكيل موثوق يرسل الموقع)، ومكان تشغيله، وسياسة الاحتفاظ ببيانات الموقع. لا يلزم حسم مزود مدفوع لإعداد مخطط SQL، لكن يلزم قبل تفعيل المؤشر الجغرافي.
6. تعريف المدينة في المؤشرات عند تنقل المستخدم بين مدينتين خلال يوم واحد، ومدة حفظ نشاط الأيام؛ تاريخ ما قبل بدء التسجيل اليومي غير قابل للاستنتاج من آخر heartbeat.

هذه القرارات لا تمنع بناء أدوات الجرد وDDL وبيئة staging، لكنها تمنع اعتماد حجم الخادم وموعد قطع الإنتاج.

## 12. مراجعة قابلية التنفيذ على `g000st-web` وعدم قطع الخدمة (30 سبتمبر 2026)

### 12.1 حقائق تحققت قراءةً فقط

- الخادم `g000st-web` لديه 3.7 GiB RAM، بلا swap، وقرص جذري 38 GiB منه نحو 25 GiB متاحة عند الفحص. لم يظهر عميل `psql` أو خدمة PostgreSQL عاملة. تعمل عليه عمليات PM2 للويب الإنتاجي القديم، ويب staging، وAPI staging، إضافة إلى Nginx وcoturn. هذه لقطة ساكنة وليست قياس ضغط أو ضمان سعة.
- `staging.g000st.com/api/v1/health` يصل إلى API الجديد على `127.0.0.1:3100`. أما `g000st.com/api/v1/health` فيرجع HTML من عملية الويب القديمة على `127.0.0.1:3000`، رغم رمز HTTP 200. إعداد الإنتاج الفعلي ومسارات العملاء المنشورين يجب جردها؛ لا نعتبر نجاح رمز 200 إثباتًا لوجود API الإنتاجي.
- `apps/api/src/server.ts` يربط جميع المجالات بـFirestore، و`AdminDeskService` و`AdminAnalyticsService` يصلان إليه مباشرة. لا يوجد driver أو مخطط PostgreSQL حاليًا. الويب والهاتف في هذا المستودع يستدعيان `/api/v1` عبر HTTP، لكن إعداد عنوان API المضمّن في نسخة الهاتف المنشورة وإعداد الويب المبني يحتاجان فحصًا فعليًا.
- `/api/v1/health` الحالي يرد `ok: true` بلا فحص قاعدة البيانات أو الخدمات الحرجة. نشر staging يعيد تشغيل API في وضع PM2 `fork` ويختبر health وsmoke محدودًا؛ هذا لا يضمن استمرار WebSocket للمكالمات. `CallingRelay` يحتفظ بالاتصالات والعروض المعلقة في ذاكرة العملية، وعامل انتهاء Chat يبدأ داخل عملية API.
- في ملف إعداد API staging توجد أسماء إعدادات Stripe وTelnyx وMinIO وTURN، ولا توجد أسماء `APNS_VOIP_*` المطلوبة لرنين iOS الأصلي حين يكون التطبيق مغلقًا. `EXPO_PUSH_ACCESS_TOKEN` غير موجود وهو اختياري ما لم تُفعّل Enhanced Push Security. وجود اسم الإعداد لا يثبت أن تكامله الخارجي يعمل؛ يُختبر فعليًا قبل القطع.

### 12.2 قرار تصفير البيانات وحدوده

| البيانات | القرار الافتراضي الذي يحافظ على تجربة العميل | شرط تغيير القرار |
| --- | --- | --- |
| الحسابات البشرية والصفحات وRecovery verifier والجلسات و`AUTH_RECOVERY_PEPPER` | نقلها كما هي حتى يبقى الدخول والتبديل بين الصفحات وrefresh يعملان | إن أُريد خروج الجميع وإنشاء حسابات جديدة، يلزم تغيير تجربة الويب والهاتف واختبارها وإبلاغ المستخدمين؛ القاعدة الفارغة وحدها تسبب 401 ومسح الجلسة. |
| صلاحية الأدمن وإعدادات `pages/parts` والرسائل التشغيلية | نقلها والتحقق منها قبل استقبال المستخدمين | لا يفتح النظام بقاعدة إعدادات افتراضية تغير سياسة الدخول أو الإظهار. |
| قيود الفوترة والأرصدة والمدفوعات وwebhooks وسجل Telnyx والمكالمات الجارية | نقلها أو تسويتها صراحة، حتى لو كان المحتوى الاجتماعي تجريبيًا | لا يجوز إسقاط التزام مالي أو حدث خارجي قابل لإعادة الإرسال بافتراض أن كل البيانات تجريبية. |
| أجهزة Expo/FCM/VoIP وتسجيلاتها | نقلها أو ضمان إعادة تسجيل ناجحة على الجهازين قبل اعتبار Push والمكالمات صالحة | إن حُذفت جميعها، لن يصل Push للأجهزة التي لم تفتح التطبيق بعد. |
| المنشورات، القوائم، العلاقات، المحادثات والوسائط | يمكن تصفيرها **فقط بعد قرار صريح** وبعد تنظيف العلاقات والملفات المرتبطة دون حذف كائن ما زال مرجوعًا إليه | إن بقي عميل يعرض نسخة محلية قديمة، يلزم إبطال cache أو إظهار حالة فارغة صحيحة. |
| سجلات الدعم والتدقيق | احتفاظ مستقل حسب السياسة؛ لا تُحذف تلقائيًا مع تصفير محتوى التجربة | يلزم قرار احتفاظ واضح واختبار واجهة الأدمن. |

الافتراض الافتراضي إلى أن يُحسم معنى «تصفير البيانات» هو **نقل الهوية والجلسات والبيانات التشغيلية والمالية، مع إمكان تصفير محتوى التجربة فقط**. يجب فحص مجموعات Firestore وأحداث Stripe/Telnyx الحقيقية قبل تصنيف أي صف بأنه قابل للمحو.

### 12.3 تشغيل PostgreSQL محليًا على الخادم

1. قبل التثبيت: تسجيل حمل RAM/CPU والقرص وIO خلال ذروة فعلية، وحجم Firestore المتوقع بعد النقل، وحجم فهارس SQL وWAL ونسخ staging المؤقتة والبناء والنشر. يُقاس زمن استعادة نسخة فعلية. إذا لم تتسع الذروة والنسخ وهوامش الإنذار داخل 3.7 GiB/38 GiB، يجهز خادم DB منفصل قبل القطع؛ إضافة swap قد تمنع قتل العمليات لكنها ليست بديلًا عن RAM أو قرص كافيين.
2. تثبيت إصدار PostgreSQL مدعوم من مستودع موثوق بعد تثبيت إصدار النظام، كخدمة `systemd` مستقلة. ضبط `listen_addresses` على localhost فقط أو Unix socket، وعدم فتح 5432 للعامة. فصل `g000st_staging` و`g000st_production` في قاعدتين وأدوار تطبيق مستقلة، ودور migrations، ودور backup؛ أذونات التطبيق محدودة وSCRAM للمصادقة. تحفظ كلمات المرور خارج Git وبصلاحيات ملفات ضيقة.
3. تحديد ميزانية اتصالات: عدد عمليات API × حجم pool، مع احتياط لعمليات migration وbackup وإدارة القاعدة. ضبط حدود زمن الاتصال والاستعلام والمعاملة، و`idle_in_transaction_session_timeout`، وبدء إعدادات الذاكرة بتحفظ ثم تعديلها بقياس. لا يبدأ عامل Chat مرتين عند التشغيل المتوازي إلا بتنسيق lease/leader واحد.
4. نسخة أساسية مشفرة وأرشفة WAL مستمرة **خارج هذا الخادم**، مع مراقبة آخر نسخة وآخر WAL ومساحة `pg_wal`. تجربة استعادة إلى مثيل منفصل قبل الإنتاج ثم دوريًا؛ وتوثيق RPO/RTO الفعليين. مراقبة الخدمة والاتصالات والصفقات العالقة والاستعلامات البطيئة والـdisk والـIO والـoutbox. نسخ MinIO منفصل. فشل هذا الخادم الواحد سيوقف التطبيق والقاعدة معًا، مهما كانت جودة النسخ الاحتياطية.
5. نشر مخطط SQL بإصدارات expand/contract قبل الكود، بمستخدم migration منفصل وقفل يمنع تشغيل نسختين من migrator. لا يُعاد نشر إصدار API سابق إذا صار المخطط غير متوافق معه. تُنقل أسرار القاعدة إلى ملفات البيئة المشتركة على الخادم بعد تجهيز التنفيذ، دون وضعها في artifact أو logs.

### 12.4 بروتوكول التحويل دون توقف ملحوظ

1. إثبات مسار كل عميل منشور: نطاق الويب الإنتاجي ونسخته، عنوان API المضمّن في Android/iOS، مسارات Nginx، WebSocket، callback للمدفوعات وTelnyx، والعامل الخلفي. لا يبدأ القطع إذا كان أي عميل نشط يستعمل backend قديمًا خارج خريطة النقل.
2. تجهيز PostgreSQL وAPI بديل على منفذ داخلي مستقل، مع نفس عقد `/api/v1` وتهيئة Stripe/Telnyx/FCM/APNs/Expo/MinIO، وhealth **جاهزية** يفحص `SELECT 1` ونسخة المخطط وإعداد الوحدات؛ يبقى `/health` البسيط للحيوية فقط. فحص HTTP يتطلب JSON ومحتوى `{ok:true}` من API المقصود، لا رمز 200 وحده. لا يوجَّه إليه مستخدمون أثناء التحضير.
3. تدريب كامل على staging بنسخة بيانات مناسبة: نقل أو تصفير وفق القرار، مقارنة المراجع والجلسات والقيود، ثم كل مسارات الويب والهاتف على جهازين حقيقيين. قياس زمن آخر مزامنة وزمن تحويل Nginx وإعادة المحاولة. إعادة التدريب حتى تصبح الخطوات قابلة للتكرار بأوامر وسجل توقيت واضحين.
4. قبل القطع الحقيقي: نسخة Firestore واستعادة PostgreSQL مجربتان، تسجيل نقطة القطع، والتأكد من أن webhooks ستصل إلى وجهة ثابتة وتُخزن أو يعاد إرسالها بمفاتيح idempotency. لا تُفعّل نسختا API كاتبتين لمصدرين مختلفين للعميل نفسه. للنقل الكامل يلزم سجل تغييرات موثوق يلتقط الكتابات منذ بداية النسخ الأولي؛ التصدير المُدار لـFirestore ليس لقطة ذرية. ولتصفير محتوى التجربة أيضًا يجب التقاط فروق **الهوية والجلسات والأرصدة** حتى لحظة القطع، وإلا قد يفشل refresh أو تُفقد عملية مالية.
5. تدخل بوابة الكتابة المصممة مسبقًا: تمنع بدء كتابات جديدة على المصدر القديم، وتنتظر اكتمال الجارية، ثم تنقل آخر فروق الهوية والمال والأحداث وتتحقق منها، وبعدها تحول Nginx للطلبات الجديدة وتفتح الكتابة على PostgreSQL. إبقاء القراءة متاحة ممكن، لكن تأخير الكتابة يظل محتملًا ويجب قياسه مقابل مهلة 15 ثانية في العملاء؛ إذا كان التأخير غير مقبول يلزم تنفيذ تمرير/طابور دائم للطلبات القابلة للإعادة مع بروتوكول idempotency شامل قبل القطع. تُراقب أول جلسة وكتابة ومحادثة وPush وwebhook وDB pool. لا تُحذف Firestore ولا الوسائط القديمة في هذا اليوم.
6. **المكالمات استثناء حاسم:** WebSocket و`pendingCalls` محليان لذاكرة عملية API. تغيير مسار الاتصالات في منتصف مكالمة قد يفقد الإشارة أو يقطع المكالمة، والتشغيل المتوازي بنسختين لا يحل تبادل الإشارة بينهما تلقائيًا. لضمان استمرار المكالمات يجب بناء وتوثيق relay مشترك أو بروتوكول drain يمنع مكالمات جديدة لحظيًا وينتظر انتهاء الجارية، مع اختبار جهازين أثناء cutover. إن لم ينجح هذا الاختبار، لا ندّعي أن الانتقال بلا توقف لكل ميزة.
7. قبل أول كتابة على PostgreSQL يمكن الرجوع إلى Firestore بتوجيه Nginx مع التحقق من الجلسات. بعد أول كتابة، الرجوع بمجرد تغيير التوجيه يضيع بيانات جديدة؛ الخطة عندئذ إصلاح PostgreSQL إلى الأمام أو إعادة مزامنة عكسية بعد إغلاق الكتابة والتحقق. تُحدد عتبات إيقاف واضحة: فشل refresh، خطأ مالي واحد، فقد webhook، انقطاع Push/مكالمة، أو اختلاف بيانات غير مفسر.

### 12.5 بوابة التوافق بين الويب والهاتف

- **Auth:** تسجيل جديد، Recovery ID قديم، refresh token قديم وتدويره، حذف وحظر، دور الأدمن، صفحات الحسابات، خروج ثم دخول. اختبار 401 المقصود على كلا العميلين إن اتُّخذ قرار حسابات فارغة.
- **Social/Market/Contacts:** feed والبحث والـcursors والاقتراحات، المتابعة والأصدقاء والتعليقات والتفاعلات والبلاغات، المحتوى المخفي، الصور والفيديو، السعر والعملة، وحقوق الوصول إلى الوسائط.
- **Chat:** محادثة خاصة وMarket، النص والصوت والمرفقات، dedupe بـ`clientMessageId`، القراءة والعدادات، إخفاء المحادثة لكل عضو، الحذف وBurn والانتهاء والـworker، وملفات MinIO بعد الحذف.
- **Notifications/Calling:** تسجيل أجهزة Expo وVoIP، Push في الخلفية، FCM Android وAPNs iOS، اتصال صوت/فيديو أمامي وخلفي، TURN، وWebSocket أثناء تبديل API.
- **Billing/Telephony/Admin:** Stripe checkout والعودة للتطبيق والويب، تكرار webhook، دفتر الرصيد، Telnyx SMS والمكالمات الخارجية، لوحة المستخدمين والفوترة، flags وlabels ورسائل الدعم وسجل التدقيق والإحصاءات.
- فحص عقود JSON والرموز والأخطاء وترتيب الصفحات ووقت UTC بين Firestore وPostgreSQL. تُنفذ الرحلات على **النسخ المنشورة فعلًا** من الويب وAndroid وiOS؛ نجاح اختبارات Store أو المتصفح المحلي وحده غير كافٍ.

### 12.6 مخاطر تمنع الوعد المطلق الآن

| الخطر | الأثر المتوقع إن تُرك كما هو | الإغلاق المطلوب |
| --- | --- | --- |
| الإنتاج الحالي يوجّه `/api/v1` إلى الويب القديم | اختبار health زائف أو انتقال لا يصل إليه المستخدمون | خريطة نشر الإنتاج وخطة توجيه API فعلية، مع تحقق JSON. |
| إعادة تشغيل PM2 وrelay داخل الذاكرة | انقطاع مكالمات أو عروض معلقة | blue/green مع drain أو relay مشترك وتجربة اتصال أثناء القطع. |
| تصفير الحسابات أو مفاتيح recovery أو الجلسات | 401 وخروج تلقائي؛ قد يحتاج المستخدم حسابًا جديدًا | نقل الهوية والجلسات أو تغيير تجربة العميل صراحة واختبارها. |
| تصفير أرصدة أو أحداث webhook حقيقية | فقد مالي أو احتساب مزدوج | جرد وتسوية ومفاتيح idempotency وحفظ الأحداث. |
| PostgreSQL على خادم 4 GiB بلا swap وبقرص 38 GiB | ضغط ذاكرة/قرص قد يسقط الويب وAPI وDB معًا | قياس الذروة والنسخ وWAL، تنبيهات وخيار نقل القاعدة إلى خادم مستقل. |
| نجاح `/health` الحالي دون استعلام SQL وsmoke محدود | مرور نشر مع قاعدة معطلة أو ميزة مفقودة | readiness حقيقي ومصفوفة E2E أعلاه وبوابات نشر مانعة. |
| إعدادات APNs VoIP غير موجودة في staging عند الفحص | لا يمكن إثبات رنين iOS الأصلي عند إغلاق التطبيق بالكامل | تجهيز الاعتمادات على بيئة الاختبار والإنتاج واختبار جهاز iOS حقيقي، أو إعلان أن الميزة غير جاهزة قبل وعد التوافق. |

**معيار البدء:** لا يُجدول القطع حتى تُحسم سياسة البيانات، ويُفحص مسار الإنتاج الفعلي، وتنجح استعادة النسخ والمصفوفة على أجهزة حقيقية، وتثبت تجربة cutover عدم فقد كتابة أو webhook أو مكالمة ضمن مستوى الخدمة المتفق عليه. الاستضافة على خادم واحد لا تقدم توافرًا عاليًا؛ إذا كان المقصود عدم توقف الخدمة حتى عند عطل الخادم، يلزم خادم قاعدة آخر وآلية تحويل تلقائي ومخدم API آخر أيضًا.
