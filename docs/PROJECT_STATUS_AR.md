## خارطة التنفيذ المستمرة للوصول إلى منتج عامل بالكامل

### منهج العمل الملزم

نعمل على الميزة كشريحة مكتملة، لا على مجموعة شاشات منفصلة: نحدد السيناريو وعقد API، ثم نبني
الخدمة والتحقق والصلاحيات في `apps/api`، ثم Expo في `apps/mobile`، ثم الويب في `apps/web`، ثم
أدوات الأدمن اللازمة، ثم الاختبارات وQA والنشر إلى staging. لا نترك أزرارًا تعمل محليًا فقط ولا
ننشئ بيانات mock في ميزة يُفترض أن تكون حقيقية.

كل ميزة جديدة يجب أن تحقق الآتي قبل الانتقال للتي بعدها:

1. تصميم وسيناريو مطابقان لمرجع العميل قدر الإمكان.
2. مصدر حقيقة واحد في الباك؛ الويب والهاتف لا يكرران قواعد الصلاحيات أو الحسابات.
3. loading وempty وoffline/error وretry وحالات الحذف/التعطيل واضحة.
4. TypeScript وعقد request/response صريحان، وفحوصات مناسبة للباك.
5. تجربة يدوية بين مستخدمين حقيقيين على الويب والهاتف قبل اعتبار الشريحة مكتملة.

### ترتيب التنفيذ المعتمد

#### 0. تثبيت البنية والنشر

- يحافظ `apps/api` على كونه الباك الوحيد المعتمد، وFirestore هي قاعدة البيانات الحالية.
- يبقى API والويب وقاعدة البيانات على الخادم الأساسي؛ الخادم الثاني لا يستخدم قبل تجهيز Object
  Storage متوافق S3، volume، صلاحيات، نسخ احتياطية، وسياسة روابط موقعة للميديا.
- يتم النشر إلى staging يدويًا فقط من GitHub Action، ثم يختبر قبل لمس الإنتاج.
- الأولوية الفورية: إصلاح `package-lock.json` وإعادة تشغيل نشر API حتى تصبح ميزات Chat الموجودة
  على `main` موجودة فعليًا على staging.

#### 1. Auth والهوية والجلسة — منجز أساسيًا

- تسجيل الدخول بحقل واحد ذي 50 محرفًا، والتسجيل من زر منفصل مع تأكيد ثم نسخ ID الجديد.
- `Public ID` للمشاركة وإضافة الآخرين؛ `Recovery ID` سرّ مستقل للاستعادة ولا يظهر في الملف العام.
- الجلسات محفوظة آمنًا على الجهاز، وRefresh/Logout يعملان عبر الباك.
- المتبقي هنا: QA كامل على staging للويب والهاتف، وإدارة أجهزة/جلسات المستخدم ضمن Profile لاحقًا.

#### 2. Chat الخاص — بُني محليًا وينتظر نشر API وQA

- محادثة فردية فقط؛ لا Groups ولا غرف عامة.
- إنشاء/فتح المحادثة بـPublic ID، إرسال نصي، retry وidempotency، pagination، unread/read، والانتقال
  لأول رسالة غير مقروءة.
- احتفاظ الرسائل ساعتين وحذف فعلي؛ Burn اختياري يفتح عند المستلم ثم يحذف بعد خمس ثوانٍ.
- تظهر حالة الطرف المحذوف مع بقاء السجل المحتفظ به ومنع الإرسال إليه.
- Push للهاتف مدمج لكن لا يعد جاهزًا فعليًا قبل EAS Project ID وFCM/APNs واختبار جهاز حقيقي.
- لا يرى الأدمن محتوى المحادثات، ولا يوصف النظام بأنه E2EE قبل تنفيذ ذلك وتدقيقه.
- المتبقي قبل إغلاق هذه الشريحة: نشر API، اختبار هاتف ↔ ويب بحسابين، اختبار pagination وBurn
  والحذف والقراءة، ثم قرار realtime بدل polling المؤقت وميزات الرد/التفاعل/المرفقات لاحقًا.

#### 3. Contacts — التالية بعد إغلاق Chat

- إضافة مستخدم بـPublic ID، ومشاركة/مسح QR حقيقي في الهاتف.
- قائمة Contacts الخاصة بـg000st: بحث، فلترة، مفضلة، وحالة online عندما تنفذ presence.
- فتح Chat الموجود نفسه أو بدء محادثة خاصة من contact؛ الاتصال يؤجل لمرحلة Mobile.
- block/remove يطبق وفق القرار النهائي: الحذف المحلي من الجهاز فقط حاليًا، ولا ينفذ حذف حساب أو
  حظر على الخادم بلا قرار صريح.
- جهات اتصال الهاتف منفصلة تمامًا عن Contacts الخاصة بـg000st، ولا تطلب صلاحيتها إلا عند استخدامها.

#### 4. ID & Profile — بعد Contacts (القادمة الآن؛ Contacts لم تُبنَ بعد — تجاوزها قرار المستخدم)

**تحديث 21 سبتمبر — نُفّذت شريحة أولى حقيقية (غير محفوظة بـcommit بعد):**

- **الباك**: أُضيف رفع صورة حقيقي عبر MinIO بنفس نمط الإرفاق المستخدم في Social (`POST
  /api/v1/social/avatar-uploads` ثم `PUT /api/v1/social/profile` مع `avatarMedia`)، بحد 3MB
  وصور فقط. التخزين الداخلي أصبح `avatarObjectKey` ويُحوَّل إلى رابط موقّع صالح 30 دقيقة عند كل
  قراءة للبروفايل (`getProfile`/`updateProfile`) — القرار المتخذ: **إعادة استخدام
  `/api/v1/social/profile` لملف ID العام** (نفس الحقول تقريبًا)، دون لمس عرض الصور بجانب المنشورات
  (خارج النطاق، ولا تراجع لأنها لم تكن مفعّلة أصلًا).
- **الموبايل والويب**: أُعيد بناء شاشة/صفحة ID بالترتيب المطلوب: صورة أولًا (قابلة للتغيير) ← اسم

  لا يُخزَّن كنص واضح ولا يمكن استرجاعه أصلًا — التحقق منه فقط عبر hash) ← حقول اختيارية
  (بلد/عمر/جنس/هواية/نبذة) ← حفظ ← تسجيل خروج (أصبح بتأكيد modal على المنصتين، لم يكن موجودًا
  بالموبايل سابقًا). التصميم على الويب أصبح مطابقًا بصريًا للموبايل (بطاقات رمادية/أحمر) بدل

  تأكيد المستخدم إن كان يريدها كخدمات حقيقية لاحقًا أو استبعادها نهائيًا من النطاق.
- التحقق: `typecheck:api`, `test:api` (19/19), `build:api`, `typecheck:mobile`, `lint:mobile`,
  `typecheck:web`, `build:web` كلها ناجحة. **لم يُشغَّل تشغيل حي على المحاكي/المتصفح بعد** لتجربة
  رفع صورة فعلية على staging.
- المتبقي: تجربة حية (upload صورة فعلي، حفظ حقول، تسجيل خروج) على الموبايل والويب معًا، ثم commit،

  لعرض/إبطال جلسات — تسجيل الخروج محلي فقط ولا يُبطل refresh token على الباك).

**حالة فعلية مؤكدة بقراءة الكود في 20 سبتمبر — الميزة غير متطابقة بين المنصتين وغير مبنية كشريحة:**

- **الباك**: لا يوجد route مخصص لـ`/users` أو `/profile` عام في `apps/api/src` (الموجود فقط:
  `auth`, `chat`, `social`, `media`, `notifications`). القيم الجاهزة أصلًا: `publicId`/`recoveryId`
  من خدمة auth (`apps/api/src/core/secrets.ts`)، و`PUT /api/v1/social/profile` الذي يغطي تقريبًا
  نفس الحقول الاختيارية المطلوبة هنا (`displayName`, `avatarUrl`, `country`, `age`, `sex`, `hobby`,
  `bio`). لا توجد بنية لإدارة الجلسات/الأجهزة، الدعم، البلاغات، أو صفحات Privacy/Terms حقيقية.
- **الهاتف** (`apps/mobile/src/features/identity/`): شاشة حقيقية صغيرة — Public ID فعلي من auth،
  نسخ حقيقي (clipboard)، Sign out حقيقي. لا يوجد Recovery ID معروض، لا صورة/ملف اختياري، لا دعم،
  لا إدارة جلسات.
- **الويب** (`apps/web/app/(user)/profile/page.tsx`، 305 سطر): واجهة مورّثة من الملف القديم لكنها
  **mock بالكامل**: البروفايل يُحفظ في `localStorage`، الصورة تُحوَّل إلى base64 محليًا بدون رفع
  حقيقي (يخالف قاعدة "لا تُستخدم روابط أو تخزين محلي كبديل لخدمة حقيقية")، رسالة الدعم مزيفة
  بـ`setTimeout`، Privacy/Terms مجرد toast. لا نداء API واحد حقيقي في هذه الصفحة عدا قراءة
  `publicId` من session.
- **قرار مطلوب قبل البناء**: إعادة استخدام `/api/v1/social/profile` لملف ID العام (نفس الحقول
  تقريبًا) بدل بناء endpoint مستقل، أم فصلهما فعليًا إذا كان القصد ملفين مختلفين (عام مقابل
  اجتماعي)؟ يجب حسم هذا مع المستخدم قبل الترميز.

المطلوب بناؤه كشريحة كاملة:

- عرض ونسخ ومشاركة Public ID وQR، وإظهار Recovery ID فقط في تدفق آمن مخصص إذا تقرر ذلك.
- ملف اختياري: الاسم والصورة والبلد والعمر والجنس والهواية والاهتمامات وفق الحقول النهائية.
- إدارة الجلسات/الأجهزة، Logout، الخصوصية، السياسات، الدعم، والبلاغات كخدمات حقيقية.
- رفع الصور لا يذهب إلى Firestore أو base64؛ يستخدم media service وروابط موقعة (متوفر أصلًا لـSocial).
- حذف الحساب الفعلي قرار مؤجل؛ ما بُني في Chat يتعامل مسبقًا مع حالة حساب غير نشط عند توفرها.
- إعادة بناء صفحة الويب من الصفر وظيفيًا (إزالة mock بالكامل)، وتوسيع شاشة الهاتف لتطابقها.

#### 5. Social — بعد Profile

Social ليست محادثة جماعية. هي Feed للمنشورات، وأي مراسلة من منشور تستخدم Chat الخاص نفسه.

- الواجهة المرجعية: Home Feed وMy Page وAlerts، مع زر إنشاء منشور وcomposer باسم مستعار افتراضيًا.
- المنشور: نص وصورة، نشر، تعديل وحذف للمالك، Like، Comment، Share/Copy link، Report، وفتح ملف الناشر.
- Follow أو `Camp`: نثبت الاسم والسلوك النهائيين قبل بناء API.
- ملف اجتماعي اختياري: صورة، بلد، عمر، جنس، هواية، ونبذة، مع إعدادات لإظهار الاسم/الهوية أو البقاء
  مجهولًا حسب سياسة الخصوصية.
- الإشعارات: likes/comments/follow عبر خدمة حقيقية، منفصلة عن إشعارات الرسائل.
- المكان المعتمد للحفاظ على المرجع: في الهاتف شاشة مستقلة خارج التابات الأساسية تُفتح من زر
  `g000st Social` داخل Chat؛ وفي الويب المسار `/social` من المدخل نفسه. لا نضيف Tab خامسًا.
- `Social Chat` القديم لا يبقى نظام رسائل مستقلًا: الضغط على Chat من منشور يفتح `/chat`/محادثة
  المستخدم الخاصة الموجودة، ثم يزال منطق الرد الآلي وبيانات `/social-chat` التجريبية.
- **محدَّث 20 سبتمبر**: Social API حقيقي منجز ومنشور جزئيًا (انظر قسم "تحديث جلسة 20 سبتمبر"
  أعلاه)؛ تاب Social موجود فعليًا في Expo ومتصل بالـAPI، وصفحة الويب `/social` متصلة بالـAPI
  أيضًا (لم تعد mock). `/social-chat` لا يزال يعيد التوجيه إلى `/social`. الناقص: moderation
  حقيقية للأدمن، ونشر فهرس Firestore، وQA كامل.
- نماذج بيانات الباك المطلوبة: `posts`, `comments`, `reactions`, `follows`, `reports`, وalerts
  المرتبطة بها، مع cursor pagination، صلاحيات المالك، rate limits، وواجهة أدمن للمراجعة.

#### 6. Mobile: calls وSMS والأرقام والدفع — بعد Social

- جهات هاتف، Favorites، Recents، Keypad، رقم فعلي من مزود يختاره العميل، SMS وCalls حقيقية عبر الباك
  وwebhooks موثقة.

- لا ننفذ مزود المكالمات أو الأسعار أو المنتجات النهائية قبل موافقة المستخدم عليها.
